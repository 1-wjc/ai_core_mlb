# RAG 파이프라인 설계문서 — MLB 기록 랩

> AI 코어 프로젝트 2회차 · 도메인: MLB 선수 기록과 세이버메트릭스
> 질문에 답할 때 기록 데이터 · 위키백과 · 지표 사전을 근거로 쓰고, 답변에 실제로 인용한 근거만 보여 주는 서비스입니다.
> 숫자는 2026-10-22 실행 기준입니다. 「색인 규모」 표의 값은 `python -m rag.indexer --all` 결과입니다.

## 1. 전체 흐름

```
[데이터 준비 — 한 번 실행]
 Lahman CSV ─┐                                      ┌─ players.json (선수 1명 = 항목 1건)
 Chadwick ID ┼─ collect/01~03 ─ build/01 · 02 · 03 ─┼─ record_docs.json (선수 × 시즌 · 팀 × 시즌 기록 문서)
 Wikidata ───┘                                      └─ season_leaders.json (메인 타임라인)
 위키백과 API ── collect/04 (선수 본인 한/영 문서) ── data/raw/wiki/docs/*.json + manifest
 직접 작성 ───── build/metrics.json (지표 사전 38개)

[색인 — rag/indexer.py]
 players.json ──────────────────────────────▶ 컬렉션 ① player_meta  (선수 1명 = 청크 1개)
 record_docs.json · 위키 문서 · 지표 사전 ──▶ 컬렉션 ② player_docs  (출처 3종, 청크 ID = 항목ID:문서ID:순번)

[질문 — rag/graph.py, LangGraph 2노드]
 retrieve: ① 메타 청크(항상) → 프롬프트 1 검색어 → ② 기록 · 위키 · 지표 사전 검색 (+ 근거 부족 시 보충 수집: 위키 검색 → 프롬프트 2 선별 → 수집 · 색인)
 generate: 프롬프트 3 → [근거 N] 이 달린 답변 → 실제 인용 근거만 화면에
```

| 영역 (명세서 1.2 프로젝트 구조) | 코드 |
|---|---|
| 데이터 준비 | `collect/` (수집), `build/` (정규화 · 지표 계산 · 한국어 표기 · 지표 사전) |
| Vector Store | `rag/indexer.py` (컬렉션 생성 · 청킹 · 임베딩 · upsert) |
| RAG 파이프라인 | `rag/graph.py` (retrieve · generate), `rag/prompts.py` (프롬프트 3개), `rag/collector.py` (질문 시 보충 수집) |
| 서비스 기능 | `rag/explore.py` (조건 탐색), `rag/team_era.py` (구단 시절 합산), `rag/lab.py` (RAG 실험실), `web/chat/similar.py` (비슷한 선수) |
| UI | `web/` (Django — 화면 `pages.py` + JSON API `views.py`, HTML · CSS · JS) |

## 2. 컬렉션 구조와 메타데이터 필드

컬렉션은 두 개입니다. 거리 척도는 코사인, 임베딩은 `text-embedding-3-large`(3072차원)입니다.

### ① `player_meta` — 항목 메타데이터 (F2001 · F2002)

| 항목 | 내용 |
|---|---|
| 단위 | 선수 1명 = 청크 1개 |
| 청크 ID | `player_id` (Baseball-Reference ID, 예: `ryuhy01`) — 고정이라 다시 색인해도 덮어쓰기만 됨 |
| 본문 (색인 텍스트) | 이름(한/영) · 투타 · 주 포지션 · 출생 · 출신 · 활약 기간 · 소속 구단 · 통산 기록(타격/투구) · 최고 시즌 · 수상 · 올스타 · 포스트시즌 · 특징 문구 |
| 메타데이터 | `player_id`, `name_ko`, `name_en`, `role`, `primary_position`, `two_way`, `first_season`, `last_season`, `birth_country`, `teams`, `title`, `url`(한국어 위키), `source`="메타데이터", 통산 숫자 필드 `bat_PA · bat_HR · bat_SB · bat_AVG · bat_OPS · bat_OPS_plus · pit_W · pit_SV · pit_SO · pit_ERA · pit_ERA_plus · pit_FIP` |

**항목 텍스트를 이렇게 구성한 이유 (명세서 2.2)**: 사용자는 이름 외에도 "통산 홈런 400개 넘는 좌타자", "사이영상 받은 일본 투수"처럼 기록 · 수상 · 출신으로 선수를 찾습니다. 그래서 통산 수치와 수상, 투타, 출신을 모두 텍스트에 넣었고, 숫자 비교가 필요한 값은 메타데이터 숫자 필드로도 넣어 조건 탐색(F2011)에서 필터로 씁니다. 특징 문구("장타력이 뛰어난 파워형 타자 (ISO .200 이상)")는 통산 지표 구간으로 코드가 생성합니다.

### ② `player_docs` — 외부 문서 (F2005 · F2016)

출처 종류(`source`) 세 가지를 한 컬렉션에 넣고, 청크마다 출처 종류를 저장해 근거에 표시합니다.

| 출처 종류 | 원천 | 청킹 | 이유 |
|---|---|---|---|
| 기록 데이터(Lahman) | Lahman CSV → 선수 × 시즌(정규 · 포스트), 팀 × 시즌 문서 | **문서 1개 = 청크 1개** | 한 시즌의 기록이 잘리면 다른 시즌 수치와 섞여 답이 틀림. 문서마다 선수명 · 시즌 · 구단을 첫 줄에 둠 |
| 영어 · 한국어 위키백과 | 선수 본인 문서(사전 배치) + 질문 시 보충 수집 문서 | **1,000자 / 겹침 200자** (`RecursiveCharacterTextSplitter`) | 서술 문서라 절 단위 의미를 살리되 한 청크에 한 사건 정도가 들어가게 |
| 지표 사전 | `build/metrics.json` (직접 작성, 38개) | **지표 1개 = 청크 1개** | 정의 · 계산식 · 해석이 한 묶음이어야 인용했을 때 완결됨 |

| 메타데이터 필드 | 쓰임 |
|---|---|
| `player_id` | **검색 범위 필터** — 선택한 선수의 문서만 검색. 빠지면 다른 선수 문서가 근거에 섞임. 지표 사전은 특정 선수가 아니므로 `_glossary` |
| `doc_id`, `seq` | 청크 ID `항목ID:문서ID:순번` 구성 (예: `ryuhy01:wiki-en-18736298:0`, `ryuhy01:rec:ryuhy01:2019:regular:0`, `_glossary:metric-FIP:0`) |
| `title`, `url`, `source` | 근거 표시 (제목 · 원문 링크 · 출처 종류) |
| `doc_type` | `season_regular` · `season_post` · `team_season` · `wiki` · `metric` — 기록 · 위키 · 지표 사전을 나눠 검색 |
| `season` | 질문에 연도가 있으면 기록 문서를 그 시즌으로 필터 |
| `related_player` | 관련 항목(선수 한국어 이름) |

**팀 시즌 문서**는 특정 선수 문서가 아니지만 `player_id` 필터 안에서 검색되어야 하므로, 그 시즌 그 팀에서 뛴 선수 범위마다 복사해 넣습니다 (ID에 선수 ID가 들어가 서로 덮어쓰지 않음, 같은 본문은 임베딩 1번).

## 3. 문서 수집 · 청킹 · 색인 흐름 (RAG 2)

1. **사전 배치 수집** (`collect/04`): 항목 선수 본인의 한국어 · 영어 위키 문서를 모두 받습니다. 명세서 F2004의 "항목 자체를 다룬 문서는 어떤 제외 규칙보다 우선해 항상 색인" 조건을 사전 배치로 충족합니다. 참고 문헌 · 외부 링크 절은 잘라 냅니다. 문서 JSON(제목 · URL · 본문 · 관련 선수 · 검색어 · 수집 경로 · 수집일)과 manifest(선수별 검색어 · 문서 ID · 파일)를 저장합니다.
2. **질문 시 보충 수집** (`rag/collector.py`): 선택한 선수의 위키 근거가 부족하면(가장 가까운 청크 거리 > 0.33) 프롬프트 1의 영어 검색어 2개로 위키백과를 검색 → 후보의 **제목 · 요약만** 프롬프트 2에 보여 줘 선별 → 고른 문서만 본문 · URL 수집 → 저장 → 청킹 · 색인 → 다시 검색합니다. 이미 검색한 검색어(`q:en:검색어`)와 이미 받은 문서(page_id)는 다시 받지 않고, 버린 후보도 manifest에 남깁니다.
3. **청킹 · 색인** (`rag/indexer.py`): 위키는 1,000/200으로 나누고 청크 앞에 `[선수: 류현진 · 영어 위키백과 · Hyun-jin Ryu]` 표지를 붙여 한국어 질문과 영어 문서를 잇습니다. 같은 ID는 upsert로 덮어쓰고, 본문이 같으면 임베딩을 다시 하지 않으며, 설정 변경으로 사라진 청크는 지웁니다 → 재색인해도 건수가 늘지 않습니다.

## 4. 검색 — 병합과 중복 제거 (F2006)

retrieve 노드가 근거 목록을 다음 순서로 만듭니다.

| 순서 | 근거 | 방법 |
|---|---|---|
| 1 | 선수 메타데이터 | 검색하지 않고 ID로 가져와 **항상 근거 1번** |
| 2 | 기록 문서 | 검색어 여러 개(프롬프트 1 검색어 + 원 질문)로 각각 검색 → **청크 ID 기준 병합 · 중복 제거**(같은 청크는 가장 가까운 거리로) → 가까운 순 `TOP_K_RECORD`(3)개. 질문에 연도가 있으면 그 시즌만 |
| 3 | 구단 시절 합산 | 질문에 구단이 나오면 그 구단에서 뛴 시즌을 코드로 합산한 근거 (시즌 중 이적한 해는 빼고 밝힘) |
| 4 | 위키 청크 | 같은 방식으로 병합 후 **MMR**로 `TOP_K_WIKI`(4)개 선택 (후보 30개, λ 0.7) |
| 5 | 지표 사전 | 질문 · 검색어에 지표 이름(별칭 포함)이 나오면 그 항목 (최대 3) |

- **기록과 위키를 나눠 검색하는 이유**: 처음엔 한 번에 Top-k를 뽑았더니, "2019년 ERA와 FIP 차이" 질문에 근거 6개가 모두 비슷한 다른 시즌 기록 문서였습니다(위키 서술 0개). 몫을 나누고 연도 필터를 넣은 뒤 2019 기록 + 위키 서술이 함께 들어옵니다.
- **비교 질문(F2010)**: 두 선수 범위를 각각 같은 방식으로 검색하고 위키 몫은 절반씩 나눕니다.

## 5. 프롬프트 세 개 (`rag/prompts.py`)

| 프롬프트 | 역할 | 입력 | 출력 형식 |
|---|---|---|---|
| **1. 검색어 추출** | "20년 경력의 MLB 기록 분석가" 역할로 근거 문서를 찾을 검색어 생성. 영어 문서가 많아 영어 검색어 우선, 한국어 1개. 연도 · 구단 · 지표명 포함, 직전 대화로 "그 해" 같은 표현을 풀어 씀 | 선수 이름(한/영) · 이전 대화 · 질문 | **JSON 배열** 3개 이하 (`["Hyun-jin Ryu 2019 season ERA", …]`). 파싱 실패 시 원 질문만으로 검색 |
| **2. 후보 선별** | ① 문서 후보: 위키 검색 결과의 **제목 · 요약만** 보고 질문에 쓸 문서를 고름 (본문을 받기 전에 버려 외부 호출을 줄임). ② 조건 탐색(F2011): 후보 선수 요약을 보고 조건 충족 여부 판정 | 선수 · 질문 · 번호 붙은 후보 목록 / 조건 · 후보 선수 요약 | ① **JSON 배열** (`[1, 3]` 또는 `[]`) ② **JSON 배열** (`[{"n": 3, "match": true, "reason": "…"}]`) |
| **3. 답변 생성** | 근거에 있는 내용만 사용, 수치는 근거 값 그대로(계산 · 반올림 금지), 주요 주장마다 `[근거 N]`, 근거가 없으면 "확인되지 않는다"(그 문장엔 근거 번호를 달지 않음), 질문한 항목만 짧게 | 선수 · 이전 대화 · 번호 붙은 근거 · 질문 | 한국어 문장 + `[근거 N]` 표기 |

프롬프트 3에는 기능에 따라 규칙을 덧붙입니다 (프롬프트 수는 세 개 유지, LangGraph 2노드 유지).
- **두 선수 비교**: 항목마다 "A 값 [근거] / B 값 [근거]", 역할이 다르면 먼저 밝힘, 근거 없는 단정 금지
- **사실 확인**: 첫 줄 "판정: 참 / 거짓 / 일부 사실 / 근거 부족", 이어서 주장 값과 근거 값을 나란히

## 6. 청크 · 중복 · Top-k를 정한 이유와 바꿨을 때의 차이

| 설정 | 값 | 정한 이유 | 바꿨을 때 (실측) |
|---|---|---|---|
| 청크 크기 / 겹침 (위키) | 1,000 / 200 | 위키 한 절(시즌 · 사건)이 대략 1~2청크에 들어가는 크기. 겹침 200은 문장이 잘려 사건 앞뒤가 끊기는 것을 막음 | 류현진 위키 청크 1,000/200 → **43개**, 500/100 → **92개**. 커쇼(보충 수집 문서 포함) 488 → 945개. 500/100은 청크가 짧아 근거 4개로 담기는 맥락이 줄고, 임시 색인 임베딩에도 약 1분 |
| 기록 문서 청킹 | 하지 않음 (문서 1개 = 청크 1개) | 표가 잘리면 수치가 다른 시즌과 섞임 | — |
| Top-k | 기록 3 · 위키 4 (+ 메타 1 · 지표 사전 · 구단 합산) | 기록은 질문 시즌(정규 · 포스트 · 팀)이면 충분, 서술은 4개면 한 사건을 여러 절에서 확인 가능 | 커쇼 "2014년 MVP 시즌 성적과 평가": 기록 3 · 위키 4 → 근거 8개 · 인용 3개 / 기록 1 · 위키 2 → 근거 4개 · 인용 2개 (사이영상 · MVP 서술은 둘 다 확보, 포스트시즌 기록은 빠짐) |
| 위키 검색 방식 | MMR, 후보 30 · λ 0.7 | 한 문서의 이웃 청크가 몰리는 것을 줄임 | 커쇼 "포스트시즌 부진과 우승": 근거끼리 평균 유사도 유사도 검색 0.771 → MMR 0.751, 2017 · 와일드카드 절이 새로 들어옴. λ 0.5는 류현진 부상 질문에 "미디어 출연 경력"이 섞여 0.7 채택 |
| 보충 수집 기준 | 가장 가까운 위키 거리 > 0.33 | 실측: 본인 문서에 내용이 있는 질문 0.23~0.32, 없는 질문 0.335~0.38 | 매 질문 수집(always)은 38초까지 걸림 → 근거 부족할 때만 |

이 값들은 모두 `rag/config.py`의 설정이며 `.env`로 바꿀 수 있습니다. `/lab/` (RAG 실험실) 화면에서 같은 질문을 두 설정으로 나란히 실행해 근거와 답변 차이를 직접 볼 수 있습니다.

## 7. 답변에 근거를 표시하는 방식 (F2007 · F2008)

1. retrieve가 근거마다 번호(N) · 출처 종류 · 제목 · URL을 붙여 프롬프트 3에 넣습니다.
2. 답변에서 `[근거 N]` 표기를 정규식으로 찾아 **실제로 인용한 번호만** 남깁니다. "확인되지 않는다" 문장 끝에 붙은 근거 번호는 코드가 떼어 냅니다.
3. 화면 질문 패널에 "근거 N건"을 펼치면 인용 근거마다 **출처 종류 · 제목 · 원문 링크**가 나오고, "인용한 본문 보기"로 실제 인용한 청크 본문을 볼 수 있습니다. 인용이 0개면 "답변에 인용된 근거가 없습니다"를 표시합니다.
4. 진행 상태에 검색어 · 문서 수집 결과(선별한 문서 제목) · 출처별 근거 수 · 소요 시간을 보여 주고, 답변은 생성되는 대로 스트리밍합니다.

## 8. 도메인 특화 기능을 이렇게 설계한 이유 (F2010 · F2011)

| 기능 | 설계 | 이유 |
|---|---|---|
| **두 선수 비교** | 두 선수 범위를 각각 검색하고 항목별로 양쪽 근거를 붙여 비교. 비교 페이지에는 통산 지표 표(코드 계산, 더 나은 값 강조) | 야구 질문의 상당수가 비교("류현진 vs 커쇼 2019")이고, LLM이 한쪽 수치를 지어내기 쉬운 유형이라 양쪽 근거를 강제 |
| **사실 확인** | 입력을 주장으로 보고 참 · 거짓 · 일부 사실 · 근거 부족으로 판정, 주장 값과 근거 값을 나란히 | 기록 주장("지터 1996 홈런 20개")은 근거 수치와 대조하면 판정 가능 — RAG의 이점이 가장 분명한 기능 |
| **구단 시절 합산** | 질문에 구단이 나오면 시즌 기록을 코드로 합산 (LLM은 계산하지 않음) | "카디널스 시절 통산"은 문서 어디에도 그대로 적혀 있지 않아 이전엔 "확인되지 않는다"였음 |
| **조건 탐색** | 숫자 조건은 규칙으로 메타데이터 필터, 투타 · 국가 · 수상은 색인 텍스트 포함 필터 → 의미 유사도 후보 → 프롬프트 2가 충족 판정 | 임베딩은 숫자 크기를 구분하지 못하고, LLM 판정만으로는 투타를 틀림(매니 라미레스를 좌타자로 판정) — 결정적인 조건은 코드로 |

## 9. 선택 이유 · 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 한국어 질문과 영어 문서의 검색 거리 | 같은 뜻 한/영 문장 코사인 0.42~0.45 (large) | 프롬프트 1이 영어 검색어를 먼저 만들고, 선수 ID 필터로 범위를 좁히고, 청크에 한/영 선수 표지를 붙임 |
| 검색 편중 (근거가 비슷한 시즌 기록으로만 채워짐) | 기록 문서끼리 문장 구조가 같아 서로 가까움 | 기록 · 위키 몫 분리 + 연도 필터 |
| 일반 설명에 근거 없는 인용 ("FIP는 투수 통제 결과만 본다 [근거 2]") | 지표 정의가 근거에 없었음 | 지표 사전을 세 번째 출처로 색인 → 정의도 근거로 인용 |
| "확인되지 않는다" 문장에 근거 번호 | 모델이 규칙을 가끔 어김 | 프롬프트 규칙 + 코드 후처리 |
| 질문 시 수집이 느림 (38초) | 검색 3회 · 한국어 위키 검색 후보 대부분 무관 · 본문 수집 · 임베딩 | 근거가 부족할 때만, 영어 검색어 2개만 → 25~30초 (수집하는 질문에서만) |
| 조건 탐색이 조건에 안 맞는 선수를 카드로 냄 | LLM 판정 오류, 임베딩은 숫자 비교 불가 | 규칙 필터(숫자 · 투타 · 국가 · 수상) + `match` 판정 + 부정 이유 문장 제외 |
| 구단별 질문에 답 못 함 | 기록이 선수 × 시즌 단위 | 구단 시절 합산 근거(이적 시즌은 제외하고 명시) |
| 계산 지표가 공식 발표 값과 소수점 차이 (류현진 2019 FIP 3.06 vs 3.10) | FIP 상수 · 리그 평균을 Lahman 리그 합계로 직접 계산 | 지표 사전 · RAG 비교 문서에 차이를 명시 (근거와 일치하는 값을 인용) |
| 피장타율 · OAA 요청 | Lahman에 피2루타 · 피3루타 · 추적 데이터가 없음 | 계산 가능한 피안타율 · 피출루율로 대체, OAA · Statcast 지표는 이용 조건 · 데이터 부재로 제외를 명시 |
| 1990년 이전 기록이 잘린 선수 (라이언 · 립켄) | 초기 범위 1990~2025 | 범위를 1901~2025로 확대 (항목 1,466 → 2,047명) |

**컬렉션을 두 개로 나눈 이유**: 선수 메타데이터는 "항상 근거"이자 조건 탐색의 검색 대상이고, 외부 문서는 "선수 범위 안에서 유사도 검색" 대상이라 쓰임이 다릅니다. 외부 문서 안에서는 출처 종류를 메타데이터로 구분해, 기록 · 위키 · 지표 사전을 한 컬렉션에서 필터로 나눠 검색합니다.

**LLM과 코드의 역할 분담**: 수치(지표 · 합산 · 비슷한 선수 · 리그 1위)는 모두 코드로 계산하고, LLM은 근거를 골라 인용하는 일만 합니다. RAG 사용 전후 비교(`docs/rag_comparison.md`)에서 RAG 없이 답한 오답 5건이 모두 세부 수치 · 계산 지표였던 것이 이 분담의 근거입니다.
