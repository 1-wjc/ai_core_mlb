### 2.2 근거 문서 수집 — 사전 배치 + 질문 시 보충 (RAG 2)
하나의 수집 코드(프롬프트 1 → 위키 검색 → 프롬프트 2 선별 → 본문 수집)를 사용한다.
- **사전 배치**: 대표 선수에 대해 미리 실행 → 영화 위키 JSON과 같은 스키마의 문서 JSON + `wiki_manifest.json`(선수별 검색어 · 선별된 문서 · 버린 문서 · 수집일)
- **질문 시 보충**: manifest에 있는 검색어는 로컬 JSON 사용(재수집 없음, NF2002), 없는 검색어만 같은 코드로 실시간 수집 후 JSON · manifest 갱신
- 미리 모으는 것은 **근거 문서**이며, 답변은 질문할 때 생성한다. 청킹 · 색인은 질문 시 수행(시연용 선수 일부는 캐시 없이 두어 실시간 수집 흐름을 보여 줌)

## 3. 파이프라인

### 3.1 정규화 — 영화 팩과 같은 두 가지 모양으로 맞춤
원천(Lahman)은 여러 테이블 · 시즌 시계열 · 숫자 위주라 제공 영화 팩과 형식이 다르다. 그대로 쓰면 "컬렉션 2개", "항목 1건 = 텍스트 1개"(F2001 · F2002)에서 벗어나므로 색인 전에 정규화한다.

- **`players.json`** (movies.json 역할): `player_id`, `name_ko`, `name_en`, 데뷔 · 마지막 시즌, 포지션, 투타, 소속 팀 이력, 수상, 통산 대표 지표, **요약 문장**(계산값으로 규칙 기반 생성, LLM 미사용 — 줄거리 역할을 해서 의미 검색 · 조건 탐색을 가능하게 함)
- **`record_docs.json`** (외부 문서 컬렉션의 기록 데이터): 선수×시즌 정규시즌 · 포스트시즌, 팀×시즌 1행 = 문서 1개. 지표는 `build/metrics.py`로 로컬 계산 (OPS+ · ERA+ 는 리그 기준값 + 구장 보정, FIP 상수는 리그 · 시즌별)
- **역할 규칙**: 출장 경기가 가장 많은 포지션이 투수면 투수, 아니면 타자. 투수의 타격 · 야수의 짧은 등판은 문서 text에서 뺀다 (값은 stats에 보관). 투타겸업(투수이면서 야수 출장 100경기 이상, 또는 타자이면서 100이닝 이상)은 둘 다 표시 → 오타니 쇼헤이 · 릭 앤키엘
- **외부 문서 JSON** (영화 위키 JSON과 같은 스키마): `page_id, title, url, text, source, player_id, related_player, search_query, collected_at`

### 3.2 컬렉션
| 컬렉션 | 내용 | 청크 ID |
|---|---|---|
| 메타데이터 | 선수 1명 = 텍스트 1개 (대표 지표는 메타데이터 필드로도 저장 → 숫자 필터) | `player_id` |
| 외부 문서 | `source`: 한국어 위키백과 / 영어 위키백과 / 기록 데이터(선수×시즌 1행 = 문서 1개, 한글 라벨 + 계산 지표) / 지표 사전 | `player_id:문서ID:순번` |

### 3.3 실행 흐름
1. **사전 색인**: Lahman · Chadwick · Wikidata → 정규화 → 메타데이터 컬렉션 + 기록 문서 · 지표 사전을 외부 문서 컬렉션에 색인
2. **근거 문서 수집** (사전 배치로 대표 선수 미리 수집 · 질문 시 manifest에 없는 검색어만 보충): 프롬프트 1이 `{검색어, 영어 검색어, 영어 질의, 지표, 시즌}` JSON 출력 → 한/영 위키 검색 → 프롬프트 2 후보 선별 (선수 자체 문서는 항상 포함) → 수집 → 문서 JSON · manifest 저장 → 질문 시 청킹 → 외부 문서 컬렉션
3. **retrieve 노드**: 선택 선수 메타데이터 항상 포함 + 그 선수 ID 범위로 외부 문서 검색(영어 질의 사용) + 필요하면 검색된 기록 값으로 조합 지표 계산(지표 등록부 함수) → 병합 · 중복 제거 → 근거 번호
4. **generate 노드** (프롬프트 3): 근거만 사용, 수치는 기록 데이터 근거 우선, 직접 계산 금지, 없으면 "확인되지 않는다"
5. **화면**: 실제 인용 근거만 출처 종류와 함께 표시

### 3.4 숫자 처리 원칙 (RAG가 숫자에 약한 이유에 대한 대응)
| 약점 | 대응 |
|---|---|
| 임베딩은 숫자 크기를 구분하지 못함 · 숫자만 다른 청크 혼동 | 선택 선수 메타데이터 항상 포함, 청크에 선수명 · 시즌 명시 |
| 비교 · 범위 · 정렬 불가, Top-k만 봄 | 숫자 조건은 메타데이터 필터로 처리 (F2011) |
| 청킹이 표를 깨뜨림 | 기록은 시즌 1행 = 문서 1개, 열 이름 포함 |
| LLM 계산 실수 | 지표는 코드로 계산, LLM은 인용만. 답변 숫자 ↔ 근거 숫자 대조 검사 |

### 3.5 지표 등록부
- 지표마다 Python 함수 + 등록 정보(한/영 이름 · 별칭 · 필요한 입력 · 리그 상수 필요 여부 · 정의 출처)
- 프롬프트 1은 등록부에 있는 지표명만 고를 수 있음 (지표 날조 방지, 프롬프트 수 3개 유지)
- 계산은 retrieve 노드 안에서 수행 (LangGraph 2노드 유지), 결과는 입력값 · 계산식 · 출처를 담은 근거 항목
- 기본 범위: OPS · ISO · BABIP · K% · BB% · WHIP · FIP · OPS+ · ERA+ (wOBA · wRC+ · WAR 제외)

### 3.6 한국어 질문 → 영어 문서
선수 ID 필터로 후보를 좁히고, 프롬프트 1의 영어 질의로 검색하고, 청크에 한/영 표지("[선수: 류현진 (Hyun-jin Ryu) · 2019]")를 붙인다. 근거 표시는 영어 제목에 한국어 이름을 병기한다. *(검색 적중률은 GMS 키 확보 후 실측)*
